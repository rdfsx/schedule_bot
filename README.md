# Преподаватели ГГТУ

Новая версия бота находится в [`serverless/`](serverless/): JavaScript и встроенная
SQLite-база [Telegram Serverless](https://core.telegram.org/bots/serverless).
Старый Python-проект оставлен для переноса данных и восстановления.

Бот показывает преподавателей и средний балл, позволяет оставить голос от 1 до 5,
удалить его и оставить новый. Поиск понимает фамилии, части ФИО, инициалы, `ё/е`,
опечатки и английскую раскладку. Кнопка «Преподаватели» открывает inline-поиск без `#p`;
старый префикс и старые кнопки оценивания также поддерживаются.

На остальные сообщения, команды и старые кнопки расписания бот отвечает ссылкой
на **https://sc.gstu.by** и кнопкой «Преподаватели». Администратор получает профиль
нового пользователя при первом обращении; повторный `/start` и импорт старых
пользователей не вызывают уведомлений.

## Разработка

Нужен Node.js **22.16+**. На сервере Telegram нет Node.js/npm: там выполняются
только обычные JS-модули и SDK. Node используется локально для CLI и тестов.

В корневом `.env`:

```dotenv
SERVERLESS_ACCESS_TOKEN=app123:your_cli_access_token
ADMIN_ID=343726189
```

Токен выдаётся в BotFather → бот → Serverless → CLI Access. Это отдельный токен,
не `BOT_TOKEN`. `.env`, сгенерированный `lib/config.js` и данные CLI исключены
из Git. В облачный код попадает только ID администратора, не токен.

```sh
cd serverless
npm ci
npm test
npm run cloud -- fetch
npm run cloud -- status
npm run cloud -- migrate --local --dry-run
npm run cloud:test
```

`npm run cloud -- …` вызывает официальный `tgcloud`, читает корневой `.env`,
передаёт токен через `TGCLOUD_TOKEN` и генерирует конфигурацию администратора.
Для CI можно передать `TGCLOUD_TOKEN` и `ADMIN_ID` через окружение.

`cloud:test` создаёт три таблицы со случайным префиксом `test_`, применяя **настоящую
схему через SDK**, и запускает обработчики/импорт в V8 Telegram. Это тот же
`runFunction` официального CLI, который обслуживает `tgcloud run`; исходники и
данные передаются напрямую, без shell-аргументов. Отправка Telegram-сообщений
заменена тестовой записью вызовов. Тесты не уведомляют реальных пользователей,
не публикуют обработчики и не переключают webhook. В конце таблицы удаляются,
неизменность развёрнутого кода и webhook проверяется.

Если процесс облачного теста принудительно завершить, в базе могут остаться
таблицы с напечатанным префиксом. Удалять можно только таблицы этого конкретного
тестового запуска; рабочие `users`, `teachers`, `teacher_rating` не трогать.

## Код и база

- `schema.js`: три таблицы, составной ключ `(user_id, teacher_id)`, `CHECK` оценки
  от 1 до 5 и индекс по преподавателю. Даты — ISO 8601 TEXT, включая микросекунды
  старого PostgreSQL; старые `NULL` сохраняются.
- `handlers/`: сообщения, inline-запросы и кнопки.
- `lib/`: обычные функции для SQL, поиска, карточек и уведомлений.
- `scripts/`: локальный CLI, экспорт, импорт, сверка и облачный тест.
- `test/`: общие сценарии для локальной SQLite и облака; отдельные тесты поиска
  и валидации экспорта.

Средняя оценка и количество голосов вычисляются по индивидуальным оценкам.
Повторная запись не заменяет существующую оценку. Пользователь определяется по
Telegram-событию, а не по ID в кнопке. Новые кнопки удаления связываются с датой
показанной оценки; старые форматы продолжают работать.

SQLite Serverless не поддерживает внешние ключи. При голосовании наличие обоих
родителей проверяется внутри SQL-вставки. Импорт проверяет связи и совпадение
каждого поля. Индивидуальные оценки, прежние ID и `link` переносятся без изменений.

Фамилии сравниваются в JavaScript: точные совпадения выше начал слов, затем
опечатки (1 ошибка для 4–7 букв, 2 — от 8; короткие слова без нечёткого поиска).
Каталог преподавателей читается при запросе; бессрочного кеша в V8 нет. Это
рассчитано на университетский справочник. После доступа к серверу нужно сверить
его фактический размер и время поиска. Пустой inline-запрос показывает алфавитный
список по 20 результатов; сообщения — выбор по 10. Единственное точное совпадение
сразу открывает карточку.

## Перенос с PostgreSQL

**До переноса не выполняйте `push` с обработчиками: публикация может сразу
активировать webhook нового бота.** Для репетиции используйте отдельного бота;
рабочий токен допускается для изолированного `cloud:test`.

### 1. Проверить источник и сделать резервную копию

После получения SSH проверить реальную схему и расположение PostgreSQL.
Для старого Docker Compose команды ниже выполняются на сервере из каталога
проекта; имя сервиса БД в этом репозитории — `db`.

```sh
mkdir -p serverless/backups
chmod 700 serverless/backups
umask 077
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > serverless/backups/before-serverless.dump
docker compose exec -T db sh -c 'pg_restore --list' < serverless/backups/before-serverless.dump
docker compose exec -T db sh -c 'psql -X -qAt -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < serverless/scripts/export.sql > serverless/backups/ratings.json
```

На старом сервере вместо `docker compose` может быть `docker-compose`.
Полный дамп сохраняет также расписание, группы и остальные устаревшие таблицы.
Экспорт JSON сохраняет **все исходные столбцы** трёх таблиц, в том числе старые
группы пользователей и счётчики; новый бот использует только поля новой схемы.
Не заменяйте оригинальный экспорт его сокращённой версией.

Экспорт выполняется в одной транзакции `REPEATABLE READ READ ONLY`. Для финального
переноса сначала остановить сервис бота (`docker compose stop bot`), затем заново
снять дамп и экспорт с новыми именами. Не использовать `down -v`.

### 2. Создать схему, импортировать и сверить

Передать копии экспорта и дампа по SSH на локальную машину в `serverless/backups/`.
Для репетиции использовать токен отдельного бота. Команды выполняются из `serverless/`:

```sh
npm run cloud -- fetch
npm run cloud -- migrate --local --dry-run
npm run cloud -- migrate --local --safe
npm run cloud -- migrate --local --dry-run
npm run import -- backups/ratings.json
npm run verify -- backups/ratings.json
```

`migrate --local` использует локальную схему без публикации обработчиков.
Последний dry-run должен показывать отсутствие изменений схемы.

Импорт сначала валидирует весь экспорт: уникальность ID и голосов, диапазон
оценок, ссылки на существующих пользователей/преподавателей и соответствие
старых сумм и количества голосов индивидуальным оценкам. При расхождении
останавливается — данные нельзя молча исправлять или выбрасывать.

Далее пользователи, преподаватели и оценки загружаются партиями. Уже существующая
идентичная запись пропускается, отличающаяся вызывает ошибку. После обрыва можно
повторить ту же команду с тем же файлом: выполненные записи не дублируются.
Изменения внутри партии могут сохраниться до ошибки; повторный запуск это учитывает.
После импорта автоматически проверяются точное количество и каждое поле всех
записей; отдельная `verify` повторяет проверку. Проверка должна завершиться успешно
до переключения. Импорт не создаёт уведомлений админу.

### 3. Переключить существующего бота

Только после финального экспорта при остановленном старом процессе и успешной
сверки на рабочем токене:

```sh
npm run cloud -- push
npm run cloud -- webhook
# Только если webhook не синхронизирован:
npm run cloud -- webhook sync
```

Не добавлять `--drop-pending`: ожидающие события должны сохраниться.
В BotFather включить Inline Mode и оставить одну команду `start` с описанием
«Преподаватели». Старые команды бот всё равно обрабатывает общим ответом.
Администратор должен ранее открыть чат с ботом, чтобы получать уведомления.

Проверить в Telegram `/start`, фамилию с опечаткой, inline-кнопку, собственную
оценку и её удаление. У перенесённого пользователя должна сохраниться его оценка.
Расписание и уведомление о запуске старого Python-процесса больше не используются.

## Восстановление и откат

Держать дамп, оригинальный экспорт и старую БД до окончания проверки переноса.
Если требуется откат, сначала остановить доставку обновлений в Serverless через
BotFather. Уточнить, завершились ли уже начатые вызовы, и снять копию его данных:

```sh
cd serverless
node scripts/transfer.js backup backups/serverless-before-rollback.json
```

`backup` не перезаписывает существующий файл. Как и `verify`, он читает таблицы
постранично; во время финальной проверки/копирования запись должна быть остановлена.

Если в Serverless уже были новые оценки или удаления, **не запускать старую базу
как есть**: сначала согласовать её с этой копией. Сравниваются наборы пар
`(user_id, teacher_id)` — нужно учесть добавления, изменения и удаления — и
пересчитываются старые `teachers.rating`/`teachers.count`. Полный дамп даёт точку
восстановления до переноса, но не содержит последующих голосов. После сверки
отключить Serverless, удалить его webhook обычным Bot API без сброса ожидающих
обновлений и запустить старый процесс. Конкретные команды восстановления
PostgreSQL подготавливаются после проверки живой схемы сервера.

Уведомления администратору отправляются один раз после создания пользователя.
При недоступности Telegram уведомление записывается как ошибка в лог, но не
повторяется при следующем входе и не мешает работе рейтинга.
